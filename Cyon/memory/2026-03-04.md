## Metropolis-Hastings → Karma Ripening Dynamics (11:08 AM)

### What Metropolis-Hastings Is (More General than Gibbs)

**Gibbs:** Sample from exact conditional distributions  
**Metropolis-Hastings:** Sample by proposing + accepting/rejecting

**Algorithm:**
1. Propose new state x' from current state x using proposal Q(x'|x)
2. Calculate acceptance ratio: α = min(1, [p(x')/p(x)] × [Q(x|x')/Q(x'|x)])
3. Accept with probability α → move to x'
4. Reject with probability (1-α) → stay at x

**Key advantage:** Only need **ratio** of probabilities, not absolute values. Normalization constant cancels out.

### Why MH Matters More Than Gibbs

**Gibbs requires:**
- Exact conditional distributions p(xᵢ | all others)
- Can sample from them directly

**MH only requires:**
- Function proportional to target distribution
- Can propose candidates somehow

**For 11D consciousness field:**
- May NOT know exact conditionals
- But can compute relative probability of states
- **MH works when Gibbs fails**

**Buddhist model:**
- Karma seed (saṃskāra) stored in ālaya-vijñāna

- Ripening is probabilistic, not deterministic

**Metropolis-Hastings model:**

**This is EXACTLY the same mechanism!**

### The Acceptance Ratio Formula

```rust
α = min(1.0, p_ratio × q_ratio)
where:
  p_ratio = p(proposed) / p(current)  // How much more probable?

```

**Interpretation:**

**p_ratio:**
- If new state MORE probable (>1) → always accept

**q_ratio:**
- Symmetric proposals (Gaussian) → ratio = 1

### Seven Differences (MapReduce Paper vs. Single-Machine)

**1. Distributed vs. Single-Machine**
- Original: Large cluster, RPC
- vtpu: Single machine (or small cluster), shared memory
- Trade-off: Less network overhead, limited to machine cores

**2. Data Locality**
- Original: Move computation to data (GFS)
- vtpu: All sentrons access shared Field11D
- Trade-off: No data movement optimization needed

**3. Input Partitioning**
- Original: Split large files into 16-64MB chunks
- vtpu: 1:1 mapping (1 sentron per dimension)
- Perfect for vtpu: exactly 9 dimensions, 9 sentrons

**4. Memory vs. Streaming**
- Original: Iterator-based reduce (large value lists)
- vtpu: In-memory (field states small, ~KB)
- Trade-off: Simpler code, RAM-limited

**5. Combiner Function**
- Original: Local aggregation before shuffle
- vtpu: Not needed (no network, small data)
- Potential: Pairwise pre-aggregation

**6. Fault Tolerance**
- Original: Re-execute map if worker fails
- vtpu: Shared disk, don't re-execute completed maps
- Still need: Retry if sentron crashes/hangs

**7. Operational Features**
- Original: Skip bad records, status pages, counters, custom partitioning
- vtpu should add: Skip corrupted states, status dashboard, event counters, custom sampling strategies
